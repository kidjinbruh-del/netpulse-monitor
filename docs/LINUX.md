# Linux: установка и проверка

Для Linux Mint 22.x: [отдельный установщик и инструкция](LINUX-MINT.md).

Требуются Python 3.12+, модуль venv, iputils-ping и iproute2.
Для Ubuntu/Debian подготовьте системные зависимости:

```bash
sudo apt-get update
sudo apt-get install python3-venv iputils-ping iproute2
bash tools/install_linux.sh
bash open_netpulse.sh
```

Установщик создаёт `.venv`, устанавливает зависимости и добавляет NetPulse в меню
приложений через `~/.local/share/applications/netpulse.desktop`. Существующий
config.json сохраняется. При первой установке панель привязана к loopback,
автопоиск и пример меша отключены. Административный доступ для запуска панели не нужен.

На сервере без графической оболочки: `bash open_netpulse.sh --no-browser`.
Повторный запуск использует работающий сервер; занятые чужие порты не освобождаются
принудительно. Логи находятся в `logs/`. Если Python называется иначе:
`NETPULSE_PYTHON=python3.12 bash tools/install_linux.sh`.

## Служба пользователя

Установщик подготавливает, но не включает службу автоматически:

```bash
systemctl --user daemon-reload
systemctl --user enable --now netpulse
systemctl --user status netpulse
```

Сначала остановите экземпляр, запущенный вручную, чтобы освободить его порт.
Для остановки службы: `systemctl --user stop netpulse`.
Служба пользователя обычно работает в рамках сеанса пользователя. Постоянный запуск
без входа требует отдельной настройки lingering администратором; установщик её не меняет.
После переноса каталога повторите установку, чтобы обновить абсолютные пути.

## Сканирование сети

Выбор сети опирается на активные IPv4-интерфейсы и их маски. Известные VPN/виртуальные
интерфейсы не выбираются первыми при наличии физического; нужную сеть можно выбрать
в интерфейсе вручную. Скан ограничен 1024 адресами, ping привязан к исходному IP.
MAC берётся из `ip -j neigh show dev ...`; при недоступности iproute2 используется
старый `arp`, если он установлен. Записи ARP показываются без обещания текущей доступности.

Программа не включает root-доступ и не меняет firewall. Доступность ping зависит
от системных прав iputils и политики сети. Отсутствие ответа не доказывает отсутствие
устройства. В контейнере/WSL NAT обычно видна виртуальная сеть, а не Ethernet хоста;
для испытаний физической LAN нужна подходящая сетевая конфигурация VM.

## Воспроизводимый Linux-стенд

Job `linux-vm-lab` в GitHub Actions запускается в отдельной Ubuntu VM. Он:

1. Устанавливает проект в настоящий Linux venv и проверяет `.desktop`/systemd unit.
2. Запускает настоящий HTTP-сервер через launch script и проверяет повторное открытие.
3. Создаёт два временных network namespace, пару veth с адресами 10.203.0.1/29
   и 10.203.0.2/29, плюс фиктивный VPN-интерфейс для проверки выбора сети.
4. Проверяет реальный ICMP, MAC, запись устройства в SQLite и восстановление снимка.
5. Отключает echo-ответы только внутри namespace тестового соседа и проверяет
   обнаружение по ARP без ложного статуса online.

Стенд не соединён с физической сетью пользователя и не имитирует проверку MikroTik.
Отчёты JSON доступны как artifact `linux-network-lab-report`.
Локальный запуск на отдельной Linux-машине:

```bash
sudo env NETPULSE_PYTHON="$PWD/.venv/bin/python" bash tools/linux_lab.sh
```

Скрипт отказывается заменять существующие namespace с теми же именами и удаляет
только созданные им namespace при завершении. На Windows WSL/гипервизор для этого
не устанавливается и перезагрузка не выполняется.

## Границы поддержки

Windows Firewall, Windows-события, отдельные WinRM/runbook-операции и DPAPI остаются
платформенными. На Linux не обещается их локальное выполнение. Уже зашифрованные
Windows DPAPI секреты нужно заменить при переносе конфигурации.
