# ТЗ: Логическая топология сети через SNMP (ARP/MAC-таблицы)

## 0. Контекст

Проект **NetPulse** — локальный центр мониторинга сети (Python 3.12+, веб на
stdlib, без внешних зависимостей кроме `psutil`). Сейчас топология — это
**SVG-карта «шлюз + эллипс устройств»**, она чисто визуальная и НЕ отражает
реальные связи между коммутаторами/устройствами (`netpulse/web/app.js`,
функция `renderMap`; данные из `/api/map` в `netpulse/server.py`).

Задача — добавить **логическую топологию**: собирать ARP- и MAC-таблицы с
управляемых коммутаторов через SNMP, строить граф связей (кто к какому
порту/устройству подключен) и рисовать честную карту сети.

## 1. Текущая архитектура (обязательно изучить перед работой)

Файлы проекта (относительно корня):

| Файл | Что там есть |

| `netpulse/server.py` | HTTP API: `/api/map`, `/api/infra`, `/api/infrascan`, `/api/infradtype` |
| `netpulse/services.py` | `MonitorService` — паттерн модулей с `start()/stop()` через `_stop_event` |

| `netpulse/web/app.js` | фронтенд SPA; `renderMap()` рисует текущую SVG-карту |
| `netpulse/web/index.html` | вкладка «Инфраструктура» |
| `AGENTS.md` | карта проекта: как добавлять фичу (паттерн), инварианты, грабли |

**Изучить обязательно:** `AGENTS.md` (паттерн добавления фичи + инварианты),

`_read_body`), `app.js` (`renderMap`, `loadInfra`).

## 2. Цель

Построить **граф связей** ЛВС:

- Коммутаторы (управляемые) опрашиваются по SNMP v2c;
- с них снимаются **MAC-таблица** (forwarding table) и **ARP-таблица**;
- по пересечению MAC с известными устройствами парка/ЛС строится карта
  «какой узел висит на каком коммутаторе/порту»;
- результат отдаётся через REST API и рисуется на вкладке «Инфраструктура».

## 3. Технические требования (по пунктам)

### 3.1. Сбор данных (бэкенд, `infra.py`)

1. Расширить существующий SNMP-код (или добавить отдельные функции) для:
   - **MAC-таблица коммутатора** — OID `.1.3.6.1.2.1.17.4.3.1.x` (BRIDGE-MIB
     `dot1dTpFdbTable`, walk по `dot1dTpFdbAddress` + `dot1dTpFdbPort`);
   - **связь порт→MAC** через `dot1dTpFdbPort` и **порт→ifIndex** через
     `.1.3.6.1.2.1.17.1.4.1.2` (`dot1dBasePortIfIndex`);
   - **Если через ARP**: **ARP-таблица маршрутизатора/коммутатора L3** —
     OID `.1.3.6.1.2.1.4.22.1.2` (IP→MAC) и `.1.3.6.1.2.1.4.22.1.3`
     (IP→ifIndex);
   - **имя/состояние интерфейса** — `.1.3.6.1.2.1.2.2.1.2` (ifDescr),
     `.1.3.6.1.2.1.2.2.1.8` (ifOperStatus), `.1.3.6.1.2.1.2.2.1.7` (ifAdminStatus).
2. **Walk**, а не только GET: добавить функцию SNMP-walk (getnext, обход
   таблицы по префиксу OID), т.к. таблицы могут быть большими.
3. Учесть **timeout/retry** и таймаут на весь опрос одного устройства
   (не блокировать цикл).
4. Сохранение результата в БД (новая таблица, напр. `topo_links`) в формате:
   - `switch_id` (host_id коммутатора), `switch_ip`, `port_ifindex`,
     `port_name`, `mac` (нормализованный: `AA:BB:...`), `ip` (если найден из
     ARP), `device_name` (если сопоставлен с парком), `first_seen`, `last_seen`.
5. Индексировать по `switch_id` и `mac`.

### 3.2. Сопоставление (маппинг MAC→устройство)

6. По + RF — собрать известные MAC из таблиц ЛС (`lan_devices` — уже есть в
   проекте: автоскан подсети, `arp -a`, vendor) и из парка (`hosts`).
   Сопоставить MAC из SNMP-таблиц с этими записями.
7. Несопоставленные MAC — показать как «неизвестные узлы» (с vendor, если
   доступен из БД).
8. Наш собственный хост (NetPulse) — тоже узел графа.

### 3.3. API (`server.py`)

9. Новый GET-эндпоинт `/api/topology`, возвращающий:
   ```json
   {
     "generated_at": "ISO",
     "switches": [
       {"id": 1, "ip": "192.168.1.2", "name": "sw-1", "ports": [
         {"ifindex": 5, "name": "GigabitEthernet1/0/5", "state": "up",
          "connected": [{"mac": "AA:BB:..", "ip": "192.168.1.50",
                         "name": "PC-1", "kind": "pc"}]}]}
     ],
     "unmapped": [{"mac": "...", "switch_ip": "...", "port_name": "..."}]
   }
   ```
10. Включить `/api/topology` в `ROUTES_GET` и в OpenAPI-описание (если оно
    генерируется из ROUTES).

### 3.4. Фронтенд (`web/app.js`, `web/index.html`)

11. Вкладка «Инфраструктура»: под существующей SVG-картой добавить блок
    «Логическая топология» + кнопку «Построить карту».
12. Отобразить **граф**: коммутаторы — крупные узлы сверху, подключённые
    устройства — под своим коммутатором, с подписью порта.
    Допустимый формат: SVG (как текущая) или вложенные списки-деревья
    (без тяжёлых библиотек — проект на vanilla JS, без CDN).
13. Неизвестные/немаппированные узлы — отдельным блоком списком.
14. Перерисовка с кэшированием (данные уже в БД; повторный запрос не должен
    триггерить новый SNMP-опрос).
15. Соблюдать существующий стиль UI (тёмная тема, chips, цвета из style.css).

### 3.5. Конфигурация и алерты

16. В `config.json` (секция `infra`) добавить `topology_scan_min` (период
    фонового опроса, 0 = выключен). Зарегистрировать в `config.py` DEFAULTS.
17. Фоновый цикл опроса — по паттерну модулей (см. AGENTS.md): отдельный
    класс/поток, останавливается через общий event.
18. При изменении топологии (новое устройство/порт) — `push_alert`
    (тип `TOPO_*`), rate-limit по аналогии с `INFRA_SCAN`.

### 3.6. Тесты

19. Юнит-тесты на парсинг SNMP-walk ответов (пример байтовой строки в тестах).
20. Тест на сопоставление MAC→устройство.
21. Тест на API `/api/topology` (мок данных из БД, без реального SNMP).
22. Вписать в существующий раннер (`tests/`), не ломая `test_netpulse`.

## 4. Границы (чего НЕ делать)

- **НЕ переписывать существующую SVG-карту** — она остаётся; новая логическая
  топология добавляется рядом.
- **НЕ использовать pysnmp** — проект на stdlib; BER-кодирование уже есть в
  `infra.py`.
- **НЕ трогать ДЕСКТОП-версию** (`main.py`, `ui/`) — только веб.
- **НЕ вводить новые внешние зависимости** (ни на бэкенд, ни на фронтенд).
- SNMP v3, LLDP/CDP, Docker, PostgreSQL — вне рамок задачи.
